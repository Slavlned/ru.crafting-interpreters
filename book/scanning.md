Первая часть любого интерпретатора или компилятора это - <span
name="lexing">сканирование/лексинг</span>. Сканер принимает необработаный код и преобразует
символы и группы в понятные кусочки -- слова и спец-символы
которые составляют грамматику языка

<aside name="lexing">

Эту часть обычно назвают "сканирование" и "лексинг" (сокращение от "лексический анализ") на порятежнии многих лет. Еще тогда, когда компьютеры были такими же большими, как Winebagos, но
памяти было меньше, чем у ваших часов, некоторые люди использовали слово «сканер» только для обозначения
фрагмент кода, который занимался чтением символов исходного кода с диска и
буферизация их в памяти. 

Сегодня загрузка исходного файла в память не представляет сложности, поэтому это редко является отдельным этапом в компиляторе. По этой причине оба термина теперь практически взаимозаменяемы.

</aside>

Сканирование это хорошая точка отправления для нас, потому что код не очень сложный --
большинство его частей это switch. Это поможет нам прогреться, прежде чем перейти
к чему-то более интересному позже. В конце этой главы у нас будет полнофункциональный,
быстрый лексер, который может взять любую строку кода Lox и отдать токены, которые
мы скормим парсеру в следующей главе.

## The Interpreter Framework

Так как это наша первая реальная глава, преждем чем сканировать код,
нам нужна база нашего интерпретатора, Jlox. Всё начинается с класса на Джаве:

```java
package com.craftinginterpreters.lox;

import java.io.BufferedReader;
import java.io.IOException;
import java.io.InputStreamReader;
import java.nio.charset.Charset;
import java.nio.file.Files;
import java.nio.file.Paths;
import java.util.List;

public class Lox {
  public static void main(String[] args) throws IOException {
    if (args.length > 1) {
      System.out.println("Usage: jlox [script]");
      System.exit(64); 
    } else if (args.length == 1) {
      runFile(args[0]);
    } else {
      runPrompt();
    }
  }
}
```

Вставьте этот текстовый файл в свой проект, зайди в своё IDE и настройте Makefile?
Или что вам ещё нужно настроить. Мы будем здесь, когда вы закончите. Хорошо? ОК!

Lox это язык для скриптинга, что значит, что он исполняет код прямо из исходников.
Здесь два пути по которому вы можете запустить код. Например с помощью команды jlox,
передавай путь к файлу:

```java
  private static void runFile(String path) throws IOException {
    byte[] bytes = Files.readAllBytes(Paths.get(path));
    run(new String(bytes, Charset.defaultCharset()));
  }
```

Если вы хотите более интимного разговора со своим интерпретатором, вы также можете запустить
это в интерактивном режиме. Запустите jlox без каких-либо аргументов, и вы попадете в
подсказку, где можно вводить и выполнять код по одной строке за раз.

```java
  private static void runPrompt() throws IOException {
    InputStreamReader input = new InputStreamReader(System.in);
    BufferedReader reader = new BufferedReader(input);

    for (;;) { 
      System.out.print("> ");
      String line = reader.readLine();
      if (line == null) break;
      run(line);
    }
  }
```

<aside name="repl">

Интерактивное написание кода также называется "REPL" (читается как "рэпл").
Это имя пришло к нам из языка Лисп, где имплементация REPL - это
обёртка циклом некоторых билт-ин функций:

```lisp
(print (eval (read))
```

Работая с встроенным вызовом, вы читаете строку ввода, преобразовываете(оцениваете) её,
выводите результат, а затем цикл повторяется заново.

</aside>

```java

    InputStreamReader input = new InputStreamReader(System.in);
    BufferedReader reader = new BufferedReader(input);

    for (;;) { 
      System.out.print("> ");
      String line = reader.readLine();
      if (line == null) break;
      run(line);
    }
  }
```

(Выйти из бесконечного цикла можно с помощью Control + C)

Оба, и интерактивное написание кода, и чтение его из файла заворачиваются вокруг
этой функции:

```java
  private static void run(String source) {
    Scanner scanner = new Scanner(source);
    List<Token> tokens = scanner.scanTokens();

    // For now, just print the tokens.
    for (Token token : tokens) {
      System.out.println(token);
    }
  }
```

Это не очень юзабельно, пока мы не написали интерпретатора, но, маленькими
шагами - не так? Сейчас, он будет выводить токены, которые нам предоставил
сканнер.

### Отлов ошибок

Пока мы все настраиваем, еще одним ключевым элементом инфраструктуры является *ловаля ошибок*. 
В учебниках об это иногда молчат, потому что это более практично.
важнее, чем формальная задача информатики. Но если вы хотите сделать
язык, который на самом деле *пригоден* для использования*, то изящная обработка ошибок жизненно важна.

Инструменты, которые наш язык предоставляет для обработки ошибок, составляют большую часть
его пользовательского интерфейса. Когда код пользователя работает, он не думает
о нашем языке вообще - он полностью сосредоточено на *их программе*. Обычно пользователи замечают нашу реализацию только тогда, когда что-то идет не так.

<span name="errors">Когда</span> это произойдет, мы должны предоставить пользователю все
информации, которая им нужна, чтобы понять, что пошло не так, и мягко направить их
обратно туда, куда они пытаются попасть. Делать хороший язык - значит
заботиться о *ловле ошибок* с самого начала интерпретатора.

<aside name="errors">

Сказав все это, для *этого* интерпретатора то, что мы построим, довольно просто. Я хотел бы поговорить об интерактивных отладчиках, статических анализаторах и других
забавных штуках, но в ручке не так много чернил.

</aside>

```java
  static void error(int line, String message) {
    report(line, "", message);
  }

  private static void report(int line, String where,
                             String message) {
    System.err.println(
        "[line " + line + "] Error" + where + ": " + message);
    hadError = true;
  }
```

Эта функция расскажет пользователю о том, что не так случилось
в его коде.

```text
Error: Неожиданная "," *гдето* в вашей программе. Удачи отыскать ошибку!
```

Это не очень полезно. Нам нужно как минимум направление к правильной линии.
Было бы хорошо также рассказать конкретнее об ошибке.
Это было бы лучше, чтобы конкретно указать пользователю на ошибку.

```text
Error: Неожиданная "," в списке аргументов!

    15 | function(first, second,);
                               ^-- Здесь.
```

Я бы хотел сделать что-то такое в этой книге, но, правда в том, что предется очень долго возиться
в коде. Хорошо для пользователей, но не очень весело для чтения книги. Мы будем
просто указывать пользователю на строку. Но, в вашем интерпретаторе, делайте так как я говорю, и
не делайте так как я делаю, в плане *ловли ошибок*.

Главная причина того, что мы встраиваем вывод ошибок в главный класс Lox --
это поле `hadError` -- есть ли ошибка.

```java
public class Lox {
  static boolean hadError = false;
```

Мы будем использовать это, чтобы убедиться, что не пытаемся выполнить код, в котором уже известна ошибка.
Кроме того, это позволит нам завершать работу с ненулевым кодом выхода, как и положено хорошему командному инструменту:

```java
run(new String(bytes, Charset.defaultCharset()));

  // Indicate an error in the exit code.
  if (hadError) System.exit(65);

}
```

Нам нужно сбрасывать этот флаг в интерактивном цикле. Если пользователь допустит ошибку, это не должно завершать всю его сессию:

```java
  run(line);
  hadError = false;

}
```

Другая причина, по которой я вынес обработку ошибок сюда, а не разместил её в сканере и других фазах, где ошибки возникают, — это напоминание о том, что хороший инженерный подход заключается в разделении кода, который генерирует ошибки, и кода, который сообщает о них.

Различные этапы обработки исходного кода могут обнаруживать ошибки, но их задача — не думать о том, как представить их пользователю. В полнофункциональной реализации языка ошибки могут отображаться разными способами: через stderr, в окне ошибок IDE, в файле журнала и т. д. Не стоит размазывать этот код по всему сканеру и парсеру.

В идеале, у нас была бы специальная абстракция — что-то вроде интерфейса <span name="reporter">"ErrorReporter"</span>, который передавался бы сканеру и парсеру, позволяя заменять стратегии обработки ошибок. В нашем простом интерпретаторе я этого не делал, но хотя бы вынес код обработки ошибок в отдельный класс.
<aside name="reporter">

Когда я впервые реализовывал jlox, у меня была именно такая система. Но я её убрал, потому что для минимального интерпретатора, описанного в этой книге, это показалось мне излишним усложнением.
</aside>

Теперь наша оболочка приложения готова. Как только у нас появится класс Scanner с методом scanTokens(), мы сможем его запустить.
Но прежде чем перейти к этому, давайте поговорим о загадочных «токенах».

## Tokens and Lexemes

Here's a line of Lox code:

```lox
var language = "lox";
```

Здесь var — это ключевое слово для объявления переменной. Эта последовательность из трёх символов 'v' 'a' 'r' имеет значение. А если вырвать три буквы из середины слова language, например, gua, то сами по себе они ничего не значат.

Вот чем занимается лексический анализ. Наша задача — просканировать список символов и сгруппировать их в минимальные последовательности, которые всё ещё что-то обозначают. Каждая из таких групп символов называется лексемой.
В приведённой строке кода лексемы следующие:
<img src="image/scanning/lexemes.png" alt="'var', 'language', '=', 'lox', ';'" />

Лексемы — это просто подстроки исходного кода. Однако в процессе их распознавания мы также выявляем дополнительную полезную информацию, такую как:
Тип лексемы

Ключевые слова являются частью грамматики языка, поэтому в парсере часто встречается код вроде «Если следующий токен — это while, то выполнить...». Это означает, что парсеру нужно знать не только то, что он нашёл лексему с каким-то идентификатором, но и то, что это зарезервированное слово, и какое именно.

<span name="ugly">Парсер</span> мог бы просто сравнивать строку с ключевыми словами, но это медленно и выглядит не очень красиво. Вместо этого, в момент распознавания лексемы мы также фиксируем, какой тип она представляет. Для каждого ключевого слова, оператора, знака пунктуации и литерала у нас есть отдельный тип:
<aside name="ugly">

В конце концов, сравнение строк сводится к анализу отдельных символов, а разве это не задача сканера?
</aside>

```java
package com.craftinginterpreters.lox;

enum TokenType {
  // Single-character tokens.
  LEFT_PAREN, RIGHT_PAREN, LEFT_BRACE, RIGHT_BRACE,
  COMMA, DOT, MINUS, PLUS, SEMICOLON, SLASH, STAR,

  // One or two character tokens.
  BANG, BANG_EQUAL,
  EQUAL, EQUAL_EQUAL,
  GREATER, GREATER_EQUAL,
  LESS, LESS_EQUAL,

  // Literals.
  IDENTIFIER, STRING, NUMBER,

  // Keywords.
  AND, CLASS, ELSE, FALSE, FUN, FOR, IF, NIL, OR,
  PRINT, RETURN, SUPER, THIS, TRUE, VAR, WHILE,

  EOF
}
```

Литеральное значение

Некоторые лексемы представляют литеральные значения — числа, строки и т. п. Поскольку сканер всё равно проходит по каждому символу литерала, чтобы правильно его распознать, он также может сразу преобразовать его в реальное значение, которое позже будет использовать интерпретатор.
Информация о местоположении

Когда мы говорили об обработке ошибок, мы выяснили, что пользователям нужно сообщать, где произошла ошибка. Отслеживание этого начинается именно здесь. В нашем простом интерпретаторе мы фиксируем только номер строки, на которой находится токен, но в более сложных реализациях также хранятся номер столбца и длина токена.
<aside name="location">

Некоторые реализации токенов хранят местоположение как два числа: смещение от начала исходного файла до начала лексемы и её длину. Сканер в любом случае знает эти данные, так что дополнительных вычислений не требуется.

Смещение можно преобразовать в строку и столбец позже, просто пересчитав символы новой строки в исходном файле. Это звучит медленно — и действительно так, но делать это нужно только тогда, когда требуется вывести строку и столбец пользователю. Большинство токенов никогда не попадают в сообщения об ошибках, так что заранее вычислять их местоположение не имеет смысла.
</aside>

Мы объединяем всю эту информацию в класс:

```java
package com.craftinginterpreters.lox;

class Token {
  final TokenType type;
  final String lexeme;
  final Object literal;
  final int line; 

  Token(TokenType type, String lexeme, Object literal, int line) {
    this.type = type;
    this.lexeme = lexeme;
    this.literal = literal;
    this.line = line;
  }

  public String toString() {
    return type + " " + lexeme + " " + literal;
  }
}
```

Это и есть токен: объект, содержащий саму лексему и все дополнительные сведения, которые узнал о ней сканер.
Регулярные языки и выражения
Теперь, когда мы знаем, что хотим получить, давайте это реализуем.
Основу сканера составляет цикл. Начиная с первого символа исходного кода,
он определяет, к какой лексеме принадлежит этот символ,
захватывает его и все последующие символы, которые являются частью этой лексемы.
Когда достигается конец лексемы, он создает токен.

Затем он возвращается в цикл и делает то же самое, начиная со следующего символа.
Так он продолжает — "поедая" символы и периодически, ну... "выдавая" токены,
пока символы не закончатся.

Часть цикла, где мы смотрим на несколько символов, чтобы определить,
какой лексеме они соответствуют, может показаться вам знакомой.
Если вы знакомы с регулярными выражениями, то, возможно, подумали
о том, чтобы определить регулярное выражение для каждого типа лексем
и использовать их для сопоставления символов.
Например, в Lox правила идентификаторов такие же, как в C.
Вот регулярное выражение, которое определяет идентификатор:

[a-zA-Z_][a-zA-Z_0-9]*  

Если вам пришли в голову регулярные выражения, то у вас отличная интуиция.
Правила, определяющие, как символы группируются в лексемы в языке программирования,
называются его <span name="theory">лексической грамматикой</span>.
В Lox, как и в большинстве языков программирования,
правила этой грамматики достаточно просты, чтобы считаться [регулярным языком][].
Это тот же самый "регулярный", что и в "регулярных выражениях".

Именно на этом основаны такие инструменты, как Lex и Flex.
Вы просто указываете им несколько регулярных выражений, и они создают для вас
полноценный сканер.

Класс Scanner

Без лишних слов, давайте создадим наш сканер.

<aside name="static-import">

Я знаю, что статические импорты считаются дурным тоном у некоторых,
но они позволяют мне не писать TokenType. по всему сканеру и парсеру.
Простите, но в книге важен каждый символ.

Мы храним исходный код в виде строки и имеем список токенов,
который будем заполнять в процессе работы.
Упомянутый выше цикл выглядит так:

```java
  List<Token> scanTokens() {
    while (!isAtEnd()) {
      // We are at the beginning of the next lexeme.
      start = current;
      scanToken();
    }

    tokens.add(new Token(EOF, "", null, line));
    return tokens;
  }
```

Он проходит по исходному коду, добавляя токены, пока символы не закончатся.
Когда работа завершена, он добавляет финальный токен "конец файла".
Это не обязательно, но делает парсер немного проще.

Этот цикл использует несколько полей для отслеживания текущей позиции в коде:

```java
  private final List<Token> tokens = new ArrayList<>();

  private int start = 0;
  private int current = 0;
  private int line = 1;


  Scanner(String source) {
```

Поля start и current — это индексы в строке,
соответствующие первому символу текущей лексемы и символу,
который мы сейчас обрабатываем.
Еще одно поле отслеживает номер строки, чтобы мы могли
указать позицию токена в коде.

Есть также вспомогательная функция, которая сообщает,
закончились ли у нас символы:

```java
  private boolean isAtEnd() {
    return current >= source.length();
  }
```

Распознавание лексем

На каждом шаге цикла мы обрабатываем один токен.
Это — самое важное в работе сканера.

Начнем с простого. Представьте, что каждая лексема состоит
только из одного символа.
В таком случае все, что нам нужно, — это считать следующий символ
и определить для него тип токена.

Некоторые лексемы в Lox действительно состоят из одного символа,
поэтому начнем с них:

```java
  private void scanToken() {
    char c = advance();
    switch (c) {
      case '(': addToken(LEFT_PAREN); break;
      case ')': addToken(RIGHT_PAREN); break;
      case '{': addToken(LEFT_BRACE); break;
      case '}': addToken(RIGHT_BRACE); break;
      case ',': addToken(COMMA); break;
      case '.': addToken(DOT); break;
      case '-': addToken(MINUS); break;
      case '+': addToken(PLUS); break;
      case ';': addToken(SEMICOLON); break;
      case '*': addToken(STAR); break; 
    }
  }
```

Нам также понадобятся несколько вспомогательных методов:

```java
  private char advance() {
    return source.charAt(current++);
  }

  private void addToken(TokenType type) {
    addToken(type, null);
  }

  private void addToken(TokenType type, Object literal) {
    String text = source.substring(start, current);
    tokens.add(new Token(type, text, literal, line));
  }
```

Метод advance() считывает следующий символ исходного кода и возвращает его.
Метод addToken() создает новый токен, используя считанный текст.
(Позже мы добавим вторую версию метода для токенов с буквальными значениями.)
Лексические ошибки
Before we get too far in, let's take a moment to think about errors at the
lexical level. What happens if a user throws a source file containing some
characters Lox doesn't use, like `@#^` at our interpreter? Right now, those
characters get silently added to the next token. That ain't right.

Метод advance() и addToken()

Метод advance() считывает следующий символ исходного кода и возвращает его.
Метод addToken() создает новый токен, используя считанный текст. (Позже мы добавим вторую версию метода для токенов с буквальными значениями.)
Лексические ошибки

Прежде чем двигаться дальше, давайте уделим минутку тому, чтобы подумать об ошибках на лексическом уровне. Что случится, если пользователь передаст нашему интерпретатору исходный файл, содержащий символы, которые Lox не использует, например @#^? Сейчас эти символы просто молча добавляются к следующему токену. Это неправильно.

Исправим это:

```java
      case '*': addToken(STAR); break; 
      default:
        Lox.error(line, "Unexpected character.");
        break;
    }
```

Обратите внимание, что ошибочный символ все равно поглощается предыдущим вызовом advance(). Это важно, чтобы мы не застряли в бесконечном цикле.

Также обратите внимание, что мы продолжаем сканирование. В программе могут быть другие ошибки. Пользователю будет удобнее, если мы выявим как можно больше ошибок за один проход. В противном случае он исправит одну маленькую ошибку, а затем появится следующая, и так далее. Такой "лови ошибку" – это не весело.

(Не беспокойтесь. Поскольку устанавливается hadError, мы никогда не попытаемся выполнить код, даже если продолжаем его сканировать.)
Операторы

Мы уже покрыли односимвольные лексемы, но это еще не все операторы Lox. Например, ! – это один символ, верно? Иногда – да, но не когда за ним следует =. В таком случае он должен быть !=. Точно так же <, >, и = могут быть за =.

Для этого нам нужно заглянуть на второй символ:

```java
      case '*': addToken(STAR); break; 
      case '!':
        addToken(match('=') ? BANG_EQUAL : BANG);
        break;
      case '=':
        addToken(match('=') ? EQUAL_EQUAL : EQUAL);
        break;
      case '<':
        addToken(match('=') ? LESS_EQUAL : LESS);
        break;
      case '>':
        addToken(match('=') ? GREATER_EQUAL : GREATER);
        break;
      default:
```

Для этого используется новый метод:

```java
  private boolean match(char expected) {
    if (isAtEnd()) return false;
    if (source.charAt(current) != expected) return false;

    current++;
    return true;
  }
```

Это что-то вроде условного advance(). Он потребляет текущий символ, только если это тот, который мы ищем.

Используя его, мы распознаем такие лексемы в два этапа. Когда мы встречаем, например, !, мы переходим к его case в switch. Он означает: "Окей, мы знаем, что лексема начинается с !". Затем мы смотрим на следующий символ, чтобы определить, имеем ли мы ! или !=.
Длинные лексемы

Мы все еще не обработали один оператор — /. Он требует особого подхода, потому что комментарии тоже начинаются с /.

```java
        break;
      case '/':
        if (match('/')) {
          // A comment goes until the end of the line.
          while (peek() != '\n' && !isAtEnd()) advance();
        } else {
          addToken(SLASH);
        }
        break;


      default:
```

Этот случай похож на другие двухсимвольные операторы, но когда мы находим второй /, мы не заканчиваем токен. Вместо этого мы продолжаем считывать символы, пока не дойдем до конца строки.

Это наша общая стратегия для обработки длинных лексем. Когда мы обнаруживаем начало такой лексемы, мы передаем управление в специальный код, который продолжает считывать символы, пока не встретит конец.

У нас есть еще один вспомогательный метод:

```java
  private char peek() {
    if (isAtEnd()) return '\0';
    return source.charAt(current);
  }
```

Это нечто вроде advance(), но без потребления символа. Это называется предсмотр (lookahead). Так как он смотрит только на текущий непрочитанный символ, у нас предсмотр в один символ. Чем меньше это число, тем быстрее работает сканер. Лексическая грамматика определяет, сколько предсмотра нам нужно. К счастью, большинству языков достаточно одного-двух символов.
Литералы строк

Теперь, когда мы разобрались с длинными лексемами, давайте рассмотрим литералы. Начнем со строк, так как они всегда начинаются с ":

```java
        break;
      case '"': string(); break;
      default:
```

Это вызывает:

```java
  private void string() {
    while (peek() != '"' && !isAtEnd()) {
      if (peek() == '\n') line++;
      advance();
    }

    if (isAtEnd()) {
      Lox.error(line, "Unterminated string.");
      return;
    }

    // The closing ".
    advance();

    // Trim the surrounding quotes.
    String value = source.substring(start + 1, current - 1);
    addToken(STRING, value);
  }
```

Как и с комментариями, мы продолжаем считывать символы, пока не встретим " — завершающий строку. Также мы обрабатываем ситуацию, когда входные данные закончились до закрытия строки, и в таком случае сообщаем об ошибке.

В Lox поддерживаются многострочные строки. Это имеет плюсы и минусы, но запрет их усложнил бы код, так что мы их оставили. Это означает, что при обнаружении новой строки внутри строки мы должны увеличивать счетчик строк.

В конце, при создании токена, мы также создаем фактическое значение строки, которое будет использоваться позже интерпретатором. Здесь это просто означает вызов substring(), чтобы удалить окружающие кавычки. Если бы Lox поддерживал escape-последовательности, вроде \n, мы бы обработали их здесь.
Числовые литералы

Все числа в Lox во время выполнения являются числами с плавающей запятой (float), но синтаксис поддерживает как целые, так и десятичные числа. Числовой литерал – это последовательность цифр, за которой может следовать . и еще одна последовательность цифр:

```lox
1234
12.34
```

Мы не допускаем начальной или конечной точки, так что эти варианты недопустимы:

```lox
.1234
1234.
```

Определяем начало числа просто по наличию цифры. Вместо множества case для каждой цифры, мы используем default:

```java
      default:
        if (isDigit(c)) {
          number();
        } else {
          Lox.error(line, "Unexpected character.");
        }

        break;
```

Это полагается на:

```java
  private boolean isDigit(char c) {
    return c >= '0' && c <= '9';
  }
```

Как только мы знаем, что у нас число, мы передаем управление в отдельный метод:

```java
  private void number() {
    while (isDigit(peek())) advance();

    // Look for a fractional part.
    if (peek() == '.' && isDigit(peekNext())) {
      // Consume the "."
      advance();

      while (isDigit(peek())) advance();
    }

    addToken(NUMBER,
        Double.parseDouble(source.substring(start, current)));
  }
```

Он читает все цифры для целой части числа. Затем проверяет наличие дробной части – точки (.) и хотя бы одной цифры после нее. Здесь требуется еще один предсмотр, так как мы не хотим потреблять . до тех пор, пока не уверены, что за ним следует цифра.

Так что мы добавляем:

```java
  private char peekNext() {
    if (current + 1 >= source.length()) return '\0';
    return source.charAt(current + 1);
  }
```

В конце мы преобразуем лексему в ее числовое значение. В интерпретаторе Lox числа представлены Double, поэтому мы создаем именно такой объект. Мы используем встроенный метод Java для парсинга, вместо того чтобы писать свой.
Зарезервированные слова и идентификаторы

Наш сканер почти готов. Осталось распознать идентификаторы и ключевые слова. Может показаться, что мы могли бы обработать ключевые слова так же, как многосимвольные операторы, например:

```java
  case 'o':
    if (peek() == 'r') {
      addToken(OR);
    }
    break;
```

Но что, если пользователь назовет переменную orchid? Тогда сканер увидит or и ошибочно распознает его как оператор.
This gets us to an important principle called <span
Принцип "максимального захвата" (Maximal Munch)

Это подводит нас к важному принципу, который называется <span name="maximal">максимальный захват</span>. Когда два правила лексического анализа могут соответствовать одной и той же части кода, выбирается то, которое охватывает наибольшее количество символов.

Этот принцип означает, что если мы можем считать orchid идентификатором, а or ключевым словом, то побеждает первое. Именно поэтому мы выше предположили, что <= должно быть считано как один токен <=, а не как <, за которым следует =.
<aside name="maximal">

Рассмотрим коварный кусочек кода на C:

```c
---a;
```

Является ли он допустимым? Это зависит от того, как лексический анализатор разобьёт лексемы. Если он увидит это так:

```c
- --a;
```

То код можно разобрать. Однако это потребовало бы от лексического анализатора знания о грамматической структуре окружающего кода, что усложнило бы его работу. Вместо этого правило максимального захвата предписывает всегда сканировать этот код так:

```c
-- -a;
```

Даже если это приводит к синтаксической ошибке на этапе разбора.
</aside>

Принцип максимального захвата означает, что мы не можем легко обнаружить зарезервированное слово, пока не дойдём до конца лексемы, которая могла бы быть идентификатором. В конце концов, зарезервированное слово является идентификатором — просто таким, которое язык зарезервировал для себя. Именно отсюда и берётся термин "зарезервированное слово".

Поэтому мы предполагаем, что любая лексема, начинающаяся с буквы или подчёркивания, является идентификатором:

```java
      default:
        if (isDigit(c)) {
          number();
        } else if (isAlpha(c)) {
          identifier();
        } else {
          Lox.error(line, "Unexpected character.");
        }
```

Затем вызывается:

```java
  private void identifier() {
    while (isAlphaNumeric(peek())) advance();

    addToken(IDENTIFIER);
  }
```

При этом используются вспомогательные функции:

```java
  private boolean isAlpha(char c) {
    return (c >= 'a' && c <= 'z') ||
           (c >= 'A' && c <= 'Z') ||
            c == '_';
  }

  private boolean isAlphaNumeric(char c) {
    return isAlpha(c) || isDigit(c);
  }
```

Теперь идентификаторы работают. Чтобы обработать ключевые слова, мы проверяем, соответствует ли идентификатор одному из зарезервированных слов. Если да, то мы используем специальный тип токена для этого ключевого слова. Этот набор зарезервированных слов определён в виде отображения:

```java
  private static final Map<String, TokenType> keywords;

  static {
    keywords = new HashMap<>();
    keywords.put("and",    AND);
    keywords.put("class",  CLASS);
    keywords.put("else",   ELSE);
    keywords.put("false",  FALSE);
    keywords.put("for",    FOR);
    keywords.put("fun",    FUN);
    keywords.put("if",     IF);
    keywords.put("nil",    NIL);
    keywords.put("or",     OR);
    keywords.put("print",  PRINT);
    keywords.put("return", RETURN);
    keywords.put("super",  SUPER);
    keywords.put("this",   THIS);
    keywords.put("true",   TRUE);
    keywords.put("var",    VAR);
    keywords.put("while",  WHILE);
  }
```

После сканирования идентификатора мы проверяем, совпадает ли он с одним из ключевых слов:

```java
    while (isAlphaNumeric(peek())) advance();
    String text = source.substring(start, current);
    TokenType type = keywords.get(text);
    if (type == null) type = IDENTIFIER;
    addToken(type);
  }
```

Если совпадает, то мы используем тип токена ключевого слова. В противном случае это обычный пользовательский идентификатор.

Замечание по дизайну: Неявные точки с запятой

Сегодняшние программисты избалованы выбором языков и стали разборчивы в синтаксисе. Они хотят, чтобы их язык выглядел чисто и современно. Один из устаревших элементов синтаксиса, который почти все новые языки выбрасывают (а некоторые старые, такие как BASIC, вообще никогда не использовали) — это явный ; в качестве завершителя оператора.

Вместо этого новая строка воспринимается как конец оператора в тех местах, где это логично. И вот это "где логично" — самая интересная часть. Хотя большинство операторов занимают одну строку, иногда требуется разделить оператор на несколько строк. Такие переносы строк не должны восприниматься как разделители.

Большинство очевидных случаев легко распознаются, но есть несколько сложных:

    Значение return на следующей строке:

```lox
return
```
"значение"

Здесь "значение" — это возвращаемое значение или у нас оператор return без значения, а затем строковый литерал?

Скобки на новой строке:

```lox
func
```
(аргумент)

Это вызов func(аргумент), или два отдельных оператора?

- на новой строке:

    first
    -second

    Это first - second (вычитание) или два отдельных оператора?

Во всех этих случаях оба варианта синтаксически допустимы, но не всегда означают то, что хотел программист. Разные языки решают эту проблему по-разному:

    Lua полностью игнорирует новые строки, но грамматика устроена так, что разделители операторов почти не нужны.
    Go определяет значимые переводы строк на уровне лексического анализатора. Если строка заканчивается на один из известных "концов операторов", перевод строки заменяется ;, иначе игнорируется.
    Python делает все переводы строк значимыми, если они не находятся внутри (), [] или {}.
    JavaScript применяет автоматическую вставку точек с запятой (ASI), которая заменяет \n на ;, только если иначе возникла бы ошибка. Это приводит к неожиданным багам и путанице.

Если ты проектируешь новый язык, почти наверняка стоит отказаться от явных точек с запятой. Главное — выбрать правила, которые соответствуют грамматике языка и не создают неожиданных проблем. Главное — не делай, как JavaScript.
